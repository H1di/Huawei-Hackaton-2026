# Бустинг (LightGBM) — версия v2

**Автор:** Евгений (Участник 3) · **Дата:** 27.10.2026 · **Код:** `booster.py`, `tl2vec.py` · **Тесты:** `test_booster.py`

## Что делает

Берёт строки, склеивает по `rowid` признаки Назара (`data/features/`) и скоры Ромы (`data/scores/`), учит LightGBM, предсказывает вероятность клика. В режиме `val` печатает AUC на val, в режиме `final` пишет `submission.csv` и сразу прогоняет `check_submission`.

```bash
python tl2vec.py --mode val                        # мои скоры tl2vec (~5 мин), см. ниже
python booster.py --mode val                       # проверка: AUC на val
python booster.py --mode val --scores item2vec     # только выбранные скоры Ромы
python booster.py --mode final                     # сабмит -> submission.csv
python test_booster.py                             # самопроверка без данных
```

## Что нужно от команды

| От кого | Файл | Режим |
|---|---|---|
| Влад | `data/split/fit.parquet`, `val.parquet`, `data/parquet/train.parquet`, `evaluation.parquet` | оба |
| Назар | `data/features/fit_features.parquet`, `val_features.parquet` | val |
| Назар | `data/features/train_features.parquet`, `eval_features.parquet` | final |
| Рома | `data/scores/<mode>/<модель>_stack.parquet` + `<модель>_target.parquet` | оба |

Признаки на 14 GB: `python make_features.py --mode val|final` вместо `python features.py`. Тот же `features.build` Назара, но кусками по событиям и для fit/train только stack-окно (`features.py` целиком падает по памяти).

Скоры подхватываются сами: любая модель, у которой есть оба файла. Колонка скора должна кончаться на `_score`.

## На чём учится и почему

Бустинг учится только на **stack-окне**: последние `STACK_DAYS` дней части (`config.windows()`). Только там у скоров Ромы нет утечки: модель A их не видела. Предсказание: val (проверка) или evaluation (финал).

Число деревьев подбирается ранней остановкой на 10% пользователей stack-окна, потом модель переучивается на всём окне. Делим по пользователям, чтобы события одного юзера не попали по обе стороны.

## Признаки, которые добавляет бустинг

Для каждого скора Ромы `<m>_score`:

| Колонка | Что значит |
|---|---|
| `<m>_score_vs_event_max` | скор минус лучший скор в событии (0 = лучший кандидат из 10) |
| `<m>_score_rank_in_event` | место по скору среди 10 кандидатов (1 = лучший) |

Текстовые колонки (если вдруг `time_bucket` строкой) кодируются числом по словарю из train.

## Защита от ошибок

- признаки не нашлись для части строк → падает (а не теряет строки молча);
- в файле признаков есть `clicked` → падает (утечка);
- у части строк нет скора → падает (окна у Ромы и тут разъехались);
- в target нет колонки, которая есть в train → падает (разные версии признаков);
- сабмит не прошёл `check_submission` → падает.

## Что сохраняется (`data/booster/`)

`lgb_<mode>.txt` (модель), `pred_<mode>.parquet` (предсказания, для сравнения версий и блендинга), `report_<mode>.json` (AUC, параметры, число деревьев).

## tl2vec — скоры «вкус юзера vs кандидат» (`tl2vec.py`)

Word2vec, но одно «предложение» на юзера (все его клики по времени, без повторов), 16 измерений, 3 сида. Почему так и что значит каждая колонка — в начале `tl2vec.py`. Главное, что нашли на val:

- сила сигнала — сходство с **средним по всей истории** (0.76), последний клик слабее (0.64): у юзера стабильный вкус;
- размерность: 8 → 0.703, 12 → 0.759, **16 → 0.765**, 24 → 0.758, 64 → 0.734;
- признаки Назара по отдельности ≤ 0.55; вектор на юзера по id (0.545) и обучение эмбеддингов на показах (0.59) переобучаются;
- в бустинг идут только признаки, не зависящие от поворота пространства: модели A и B — разные обучения word2vec.
